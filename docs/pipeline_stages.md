# Pipeline Stages — Detailed Reference

Fifteen steps in four phases. Most read a JSONL and write `success.jsonl` + `failed.jsonl`
through `PipelineRunner`, with per-item parallelism, retry, and crash recovery. Three
(`plan_sequences`, `execute_sequences`, `export_dataset`) are deterministic batch steps that
bypass all of that and write their own files.

```bash
vulcan --env quickstart --stage generate_tools        # one stage
vulcan --env quickstart --pipeline                  # all fifteen, in order
vulcan --env quickstart --pipeline --start generate_trajectories --end judge_trajectories
python -m vulcan.cli --list-steps                   # same CLI, module form
```

Ordering and input resolution live in [`vulcan/core/stage_runner.py`](../vulcan/core/stage_runner.py)
(`PIPELINE_ORDER`, `_STANDARD_INPUT`); steps do not describe their own predecessors. Defaults
quoted below come from the packaged [`vulcan/config/base.yaml`](../vulcan/config/base.yaml);
`./configs/<name>.yaml` in your working directory is deep-merged over it and wins.
Precedence is `steps.<stage>` > `defaults` > `base.yaml`.

> **`generate_tools`, `debug_environment`, `execute_sequences`, and `generate_trajectories` execute model-generated
> Python in this process, with no sandbox.** That is how the pipeline works, not an accident.
> Read the warning at the top of the [README](../README.md) before running any of
> it.

---

## Phase 1: Environment Simulation

Turns raw API specifications into a single executable, fully in-memory Python class per
category.

### 1. normalize_specs

**Purpose:** Validate spec consistency and fill in missing response schemas.

**Input:** built by the runner, not by a previous step. `StageRunner._run_normalize_specs`
reads `environment.get_api_catalog(category)`, writes
`<category>/normalize_specs/input.jsonl` as one record
`{"category_name": …, "api_list": [...]}` (plus `policy_rules` when the category has any),
then the step's `preprocess_input` flattens that into **one item per API**, carrying
`function` and `constraints`.

**Process:**
1. Ask the model whether `name` and `description` agree. `PASS` ends it; `PROBLEM` returns a
   corrected spec inside `<json_schema>` tags. Up to 5 attempts.
2. If the spec has no `response` field, generate one from the description and parameters.
   Up to 5 attempts, and the result must actually contain a `response` key.

**Output fields:** `normalized_schema` — **written on every path**: the resolved spec,
corrected when step 1 found a problem and carrying a `response` schema either from the catalog
or generated by step 2. That single field is the contract with every later step.
`normalized_function` is written only when step 1 found a problem and is **diagnostic**: it
records that a name/description correction happened. Nothing selects on it.

**Config:** `max_tokens` (16000).

⚠ **This step has no validator**, so every row lands in `success.jsonl` — including rows
where every model call failed. Steps swallow per-item `LLMError` and return the item
unchanged; for the other stages a validator catches the consequence, but not here. The
honest signal is `llm_calls=` in `<output_base>/logs/<category>/normalize_specs.log`. Such a
row also reaches `success.jsonl` without `normalized_schema`, which is what `build_graph`
later refuses to run on.

⚠ **Both agents are constructed with `temperature=0`.** Setting
`steps.normalize_specs.temperature` does nothing.

The shipped example catalogs already carry a `response` schema on every tool and describe it
consistently, so step 2 normally has nothing to generate and `normalized_function` normally
stays absent — the cheap, good case, not a failure. `normalized_schema` is written either
way.

---

### 2. generate_tools

**Purpose:** Generate a Python `Tool` class implementing one API.

**Input:** `normalize_specs/success.jsonl`.

**Process:**
1. Generate the class. If the item has a `constraints` string, the constraint-aware
   system/user prompt pair is used instead of the plain one.
2. A modifier agent reviews the code; its rewrite is accepted only when its `<decision>`
   contains `Problem`.
3. `load_api_class()` executes the code. If that raises, an executor agent gets the traceback
   and returns `<verified_code>`.

**Generated code pattern:**
```python
class MyApiTool(Tool):
    @staticmethod
    def invoke(data: Dict[str, Any], param1: type, ...) -> str:
        # all state comes from `data` — never a real filesystem, socket, or database
        return json.dumps({...})

    @staticmethod
    def get_info() -> Dict[str, Any]:
        return {"type": "function", "function": {...}}
```

**Output fields:** `tool_code`, `decision`.

**Validator** (`validators/deterministic.py`): `tool_code` present, `decision` free of
`Execution Erro`, `load_api_class()` succeeds, the class exposes callable `invoke` and
`get_info`, and **every `invoke()` parameter is referenced in its body** (AST check).

**Config:** `temperature: 0`, `max_tokens: 32000`.

⚠ **The unused-parameter check is the most common cause of `failed.jsonl` rows here.** A
generated `invoke()` that accepts an optional parameter and quietly ignores it fails the whole
item. That is deliberate — a tool that ignores an argument produces trajectories where the
argument does not matter.

⚠ **Constraint awareness is per API, not per environment.** It keys off `"constraints" in inp`,
which `normalize_specs` copies from the catalog entry. `policy_rules` never reaches this step.

---

### 3. verify_tools

**Purpose:** Iteratively verify and repair the generated API code against its spec.

**Input:** `generate_tools/success.jsonl`.

**Process** — loop up to `max_fix_iterations` (5):
1. A verifier agent checks the code against the spec and returns `<decision>` + `<modified_code>`.
2. If the decision contains `PROBLE` and code came back, execute it; on failure hand the
   traceback to the executor agent.
3. Run `find_unused_invoke_params` again; if anything is unused, re-prompt with the list and
   accept the rewrite only if it compiles.
4. Exit early when the decision contains `FINE` **and** nothing is unused.

After the loop, one more informational name/description check.

**Output fields:** `tool_code`, `verification_iterations` (one dict per round),
`py_verification_decision`, `verification_iteration_count`, `check_name_description`.

**Validator:** identical to `generate_tools`. `check_name_description` is recorded but never
blocks.

**Config:** `temperature: 0`, `max_tokens: 32000`, `max_fix_iterations: 5`.

⚠ **`env_grouped/success.jsonl` is written here but is not a step.** After the stage,
`StageRunner._build_env_grouped` regroups the per-API rows into one record per category:
`{"category_name": …, "api_list": [{function, tool_code, normalized_function, normalized_schema}]}`,
keeping only APIs that have a `tool_code`. Both `assemble_environment` and `build_graph` read it.
If nothing survives, it is skipped and both of those stages fail with `input not found`.

⚠ **`_build_env_grouped` writes all four per-API keys unconditionally**, via `.get()`, so every
key is present on every row whatever its value — `normalized_function: null` is the normal case
for an API that needed no correction. Select on the **value**, never on key presence: `if
"normalized_schema" in api` matches here even when the value is `null`. A presence test is what
once let a catalog that already shipped `response` schemas serialise `null` into the
`build_graph` prompt and return an empty graph from a full-price run. `normalized_schema`
itself is now written for every API by `normalize_specs`, and `build_graph` raises `StepError`
rather than reading anything else — see [its input contract](#8-build_graph).

⚠ The control flow matches on substrings: `PROBLE` and `FINE` here, `Problem` (capitalised,
exact) in `generate_tools` and `assemble_environment`. A model that words its verdict differently
silently burns every iteration.

---

### 4. assemble_environment

**Purpose:** Merge the per-API `Tool` classes into one environment class for the category.

**Input:** `env_grouped/success.jsonl` — one item per category.

**Process:**
1. `strip_get_info()` reduces each API class to its `invoke` body; those are concatenated with
   the tool specs and sent to the generator.
2. A verifier agent checks the class against the specs; its rewrite is accepted only when
   `<decision>` contains `Problem`.
3. `execute_class_code()` runs it; on failure the executor agent gets the traceback.

**Generated code pattern:**
```python
class EnvironmentName:
    def __init__(self, initial_state: dict = None):
        self.state = initial_state if initial_state else { ... }   # must be non-empty

    def function_name_mapping(self) -> dict:
        return {"spec_tool_name": self.method_name, ...}

    def method_name(self, param1: type, ...) -> str:
        return json.dumps({...})
```

**Output fields:** `tool_code` (the unified class), `decision` (only on the failure path).

**Validator:** the class must execute, instantiate (bare `cls()`, else `cls(initial_state={})`),
expose `function_name_mapping()` returning a **non-empty dict of callables**, have a non-empty
state, and **cover every tool name in `api_list`**.

**Config:** `temperature: 0`, `max_tokens: 65000` (it is combining every class in the category).

⚠ **There is exactly one item per category here**, so a single missing tool in
`function_name_mapping()` means `success=0` for that category and the pipeline stops there.
The failure reason is in `failed.jsonl` under `_validation_reason`.

⚠ Parameter names in the merged methods must match the spec names exactly. Nothing enforces
that at this stage — `debug_environment` does, one stage later, and repairs are more expensive there.

---

### 5. debug_environment

**Purpose:** Test the environment class and fix it until the tests pass.

**Input:** `assemble_environment/success.jsonl`.

**Process:**
- **Step 0 — parameter validation.** Compare `inspect.signature()` of every mapped method
  against the spec's `properties`. Mismatches go to the fixer agent, up to `max_fix_iterations`
  rounds. Still mismatched afterwards ⇒ the item is returned with `environment_ready: False`
  and `param_validation_failed: True`, and nothing else runs.
- **Step 0.5 — test state.** Generate one realistic initial state, reusing the `generate_states`
  prompt (with `MIN_LIST_VALUES` hardcoded to `5` here).
- **Loop, up to `max_fix_iterations`:**
  1. Generate test code (retried up to `max_test_generation_retries` until the output actually
     contains `PASS:` / `FAIL:` / `SUMMARY:` and no crash marker).
  2. Execute it with `exec()` in a fresh module namespace, capturing stdout/stderr. Test
     functions named `test_*` / `run_tests` / `main` are auto-called if nothing printed.
  3. An analysis agent returns a `<verdict>`.
  4. On `ALL_PASSED`, the **state-awareness gate** runs before the item is allowed to pass.
  5. Otherwise the fixer agent rewrites the class; the rewrite is kept only if it compiles.

**The state-awareness gate** is the most valuable part of this step. An AST pass flags methods
that build large hardcoded dict/list literals or never read `self.state` despite being
data-retrieval methods. Each suspect is then confirmed by a **differential test**: instantiate
the class twice with two deliberately different states and call the method with synthesised
arguments. Identical output confirms the bug. Confirmed issues are sent to the fixer and the
loop continues (`status: STATE_AWARENESS_FIX`) — a class whose tools return the same answer
regardless of the initial state cannot produce useful training data.

**Output fields:** `environment_ready`, `tool_code`, `test_iterations` (test code truncated
to 2000 chars, output to 1000, code to 5000), `param_validation_failed`.

**Validator:** strict — `environment_ready is not True` fails the item.

**Config:** `temperature: 0`, `max_tokens: 65000`, `max_fix_iterations: 15`,
`max_test_generation_retries: 5`. (When those keys are absent entirely the class defaults are `3`
and `3`; `base.yaml` supplies 15/5. The shipped configs lower **`max_fix_iterations` only** —
6 in `quickstart` and `mock_test`, 8 in `hotel_policy`; none of them override
`max_test_generation_retries`, so it stays at 5.)

⚠ **This is the dominant Phase-1 cost.** Every iteration is at least three model calls — test
generation, analysis, fix — and test generation alone can retry `max_test_generation_retries` times,
while the state-awareness gate can add whole extra iterations after the tests already passed.
`max_fix_iterations` is the knob.

⚠ **Model-written test code is `exec()`d in this process**, and `_execute_tests` temporarily
reassigns `sys.stdout`/`sys.stderr` to capture it.

⚠ After a failing round the *same* test code is reused up to 3 times before new tests are
generated. That bound is a hardcoded `_MAX_SAME_TEST_RETRIES = 3` inside `run()`, not a config
key.

### 6. generate_states

**Purpose:** Generate diverse initial state dictionaries for the environment.

**Input:** `debug_environment/success.jsonl`. `preprocess_input` **explodes** the one item per
category into `num_states` items, so each state is one parallel model call.

**Process:** one call per item; JSON is parsed with a fallback repair agent; a list response is
unwrapped to its first element; the result is quality-checked.

**Output fields:** `initial_state` (dict or `None`), `_filter_reason` (set when the quality
check rejected it).

**The quality check (`_check_state_values`) looks at the top level only:** any top-level value
that is `None` or `""` fails, and any **top-level** list shorter than `min_list_length` fails.
Nested lists (a user with one role) are left alone deliberately.

**Validator:** `initial_state` must be a non-empty dict, so filtered items land in
`failed.jsonl`.

**Config:** `temperature: 0.8` (diversity is the whole point), `max_tokens: 32000`,
`num_states: 5000`, `min_list_length: 5`.

⚠ **`num_states` is the number of model calls for this stage, per category** (their
concurrency is `defaults.parallel_workers`). The `base.yaml` value of 5000 is a production
number; [`configs/quickstart.yaml`](../configs/quickstart.yaml) sets it to 5. Raise it only
after a full run has succeeded — these states are the only source of data diversity
downstream, so it is also the first knob to raise when the output looks repetitive.

⚠ `min_list_length: 5` against a small toy catalog rejects a lot of otherwise fine states. The
shipped configs lower it to 2–3.

---

### 7. sample_arguments

**Purpose:** Produce example call arguments for every tool, per initial state.

**Input:** `generate_states/success.jsonl` — one item per state, since different states imply
different valid arguments.

**Process:** the tool names come from `env.get_api_catalog(category)` — the **input catalog**,
filtered to tools whose spec has non-empty `parameters.properties` — not from the generated
class. Up to 3 attempts; the attempt covering the most tool names is kept, with the missing
names fed back between attempts.

**Output fields:** `functions` — the list `execute_sequences` later mines for arguments.

**Validator:** `functions` must be a non-empty list.

**Config:** `max_tokens: 32000`.

⚠ **The generating agent's temperature is hardcoded to `0.7`.** `steps.sample_arguments.temperature`
(`0.2` in `base.yaml`) is not used.

⚠ **A tool whose spec declares no `properties` is silently excluded** from the requested names,
so it gets no samples, and `execute_sequences` will have no argument source for it beyond explicit
graph edges.

## Phase 2: Graph Construction & Sequence Selection

Builds the tool dependency graph and turns it into multi-turn call sequences.

### 8. build_graph

**Purpose:** Generate directed dependency edges between tools.

**Input:** `env_grouped/success.jsonl`.

**Process:** for every **ordered pair** of distinct tools, one model call asking whether an edge
exists. Each answer is `<graph>`-tagged JSON: `{"type": "explicit"|"implicit", "arguments": …,
"source_arguments": [...], "target_arguments": [...]}`, or nothing.

- `explicit` — an output field of the source feeds an input parameter of the target.
- `implicit` — no data flows, but the source should logically precede the target.

**Output fields:** `graph` — a list of `{"source": name, "all_edges": [{"target": name,
"edges": {...} | null}]}`.

**Validator:** `graph` present and non-empty.

**Config:** `temperature: 0`, `max_tokens: 2048`.

⚠ **The spec sent to the model is `normalized_schema`, with no fallback.** `_get_api_spec`
reads that one field and raises `StepError` naming the API and the category when it is missing
or null — meaning the row never came through `normalize_specs`. It deliberately does **not**
fall back to the raw catalog `function`: an `explicit` edge can only be detected from the
`response` schema, and the catalog spec carries one only when the author supplied it, so a
fallback would silently downgrade the whole category to ordering-only `implicit` edges instead
of failing. Rerun `normalize_specs` for the category. The contract is locked in by
[`tests/test_spec_contract.py`](../tests/test_spec_contract.py).

⚠ **This stage costs *n·(n−1)* model calls per category.** 8 tools → 56; 10 → 90; 13 → 156;
22 → 462. It is the easiest way to spend far more than you intended, and the reason the
example catalogs are small.

⚠ **`max_tokens` is read straight from `steps.build_graph` with its own `2048` fallback**, so
`defaults.max_tokens` does not apply here. The prompt asks for short structured output; if you
see truncated JSON, raise the step-level key.

⚠ **The validator passes a graph whose every edge is `null`.** Parse failures and non-edges are
indistinguishable in the output, and every downstream consumer keeps only edges whose `type` is
exactly `explicit` or `implicit`. An all-null graph yields zero subgraphs one stage later, with
no error anywhere.

⚠ Every API in the category must carry `normalized_schema`, which `normalize_specs` writes for
all of them. `build_graph` reads that field alone and raises `StepError` naming the API if it is
missing, rather than falling back to the raw catalog spec — a fallback would quietly downgrade
the graph to ordering-only edges for any tool whose catalog entry omitted `response`.

### 9. plan_sequences

**Purpose:** Extract subgraphs and build multi-turn tool-calling sequences.

**Type:** deterministic (`requires_llm = False`). Run through `run_batch(input_path, output_dir)`,
**not** `PipelineRunner` — so no `success.jsonl`, no `failed.jsonl`, no retry, and no resume.
Re-running it recomputes everything.

**Input:** `build_graph/success.jsonl`.

Two independent extractors feed one merged output.

**Approach 1 — good subgraphs → sequences.**
1. Grow connected candidate subgraphs of 2 … `max_tools_per_sequence` nodes from every root by
   edge-guided BFS, score them, and reduce each to an acyclic single-leaf shape. Cap per
   category at `max_subgraphs_per_category` (5000).
2. Build a **meta-graph** over those subgraphs: `A → B` exists when A and B share no node and at
   least one graph edge runs from A's single leaf into B. Weight = explicit bridges +
   `0.5 ×` implicit bridges.
3. Enumerate `k`-length paths in the meta-graph for each `k` in `turns_per_sequence`. Every path is a
   valid multi-turn sequence **by construction** — one subgraph per turn, no node reuse, a real
   bridge edge between consecutive turns.
4. Select for diversity (group paths by covered node set, take the best from each group, then
   the second-best, …).
5. Drop sequences that are strict prefixes of longer ones, then balance-sample across
   `(category, number_turns)` down to `sequences_per_category`.

**Approach 2 — multipath subgraphs** (`enable_multipath`, default `false`).
A **multipath** region is a fork–merge (diamond) topology: two non-adjacent nodes joined by
**several distinct indirect paths**, so one query admits several valid tool orderings. For every
ordered pair `(u, v)` with no direct edge, enumerate directed paths (≤ 20 paths, depth ≤ 8);
two or more makes `(u, v)` a multipath pair. The union of nodes over all of that pair's paths
is the subgraph; subgraphs are deduplicated by node set and skipped when the union exceeds
`max_multipath_tools`. `multipath_strength` is the largest path count among the pairs that
produced it.

**Output files** (under `<category>/plan_sequences/`):
```
good_graph_<cat>.json            per-category good subgraphs
sequences_<cat>.jsonl            per-category sequences
multipath_<cat>.jsonl            only when enable_multipath
multi_turn/all_multipath.jsonl   only when enable_multipath
multi_turn/sequences_only.jsonl  the sampled sequences, for inspection
multi_turn/all_sequences.jsonl   ← merged: sequences + multipath. This is the
                                   file everything downstream reads.
```

**The two record types have different shapes**, and every consumer branches on `type`:

| | sequence | multipath |
|---|---|---|
| `id` | `seq_<n>` | `mp_<n>` |
| `type` | `"sequence"` | `"multipath"` |
| shape | `number_turns`, `sequence: [{graph_info: {nodes, edges, popularity}}]`, `bridge_weight` | `nodes`, `edges`, `multipath_pairs`, `multipath_strength`, `size`, `num_edges` |
| `number_turns` | set | **absent** |

**Config:** `max_tools_per_sequence: 5`, `max_multipath_tools: 15`, `implicit_edge_weight: 0.01`,
`sequences_per_category: 15000`, `turns_per_sequence: "2,3,4"`, `enable_multipath: false`,
`max_subgraphs_per_category: 5000` (not in `base.yaml`; the code default applies).

⚠ **`turns_per_sequence: "1"` produces no multi-turn data at all**, while the rows are still
stamped `class_multi_turn` and still land in `all_sequences.jsonl`.

⚠ **`sequences_per_category` is per category.** `StageRunner` dispatches this stage once per
category, so each gets the full budget; `target_per_k` is `sequences_per_category // len(turns_per_sequence)`,
and the final balanced sample splits the same budget across `(category, number_turns)` groups.

⚠ **A `k` larger than the number of good subgraphs is skipped silently** (`k=4` with three
subgraphs prints one line and moves on). Small catalogs quietly produce only 2-turn data.

⚠ **The `implicit_edge_weight` key governs only half of what its name suggests.** The config
value (0.01) weights implicit edges during subgraph extraction and popularity sampling;
`build_sequences` is called with a hardcoded `implicit_edge_weight=0.5` for bridge scoring
between turns, which no config key reaches.

⚠ `enable_multipath` is off by default because the pair scan is O(n²) path enumerations and
gets slow on dense graphs. Turn it on when you want queries with several correct orderings —
and expect `score_sequences` to mis-handle the records (below).

### 10. score_sequences — optional, analysis only

**Purpose:** Score sequence quality with a model.

**Input:** `plan_sequences/multi_turn/all_sequences.jsonl` — the **sequences**, not
`build_graph`'s raw graph (`_STANDARD_INPUT` in `core/stage_runner.py`).

**Process:** filter the API specs down to the nodes in the record, send them with the sequence,
and parse an `<out_judgment>` block scoring data-flow quality, coherence, complexity, and
diversity.

**Output fields:** `judgment`.

**Validator:** `judgment` present and not `None`.

**Config:** `temperature: 0`, `max_tokens: 16000`, `thinking_model: true`.

**It filters nothing, and nothing downstream reads it.** `execute_sequences` goes straight to
`plan_sequences`. Run it while tuning `plan_sequences`; skip it otherwise — a model call per sample
is the easiest cost in the pipeline to cut. There is no config switch for skipping: `--pipeline`
runs everything in `PIPELINE_ORDER`, so use `--start`/`--end` around it, or run stages
individually.

⚠ **Record shape decides how the graph is read**, and the two shapes differ. A multipath
record is matched on `type == "multipath"` and read from its top-level `nodes` / `edges`,
because `plan_sequences` never sets `number_turns` on one. A sequence record with
`number_turns > 1` is read from `sequence[*].graph_info`. Only a record that genuinely
carries `number_turns == 1` falls back to the top-level `graph_info` key. Dispatching on
`number_turns` alone sent every multipath record down that last path and billed the model to
score `{"nodes": [], "edges": []}`; `tests/test_score_sequences_records.py` covers all three
shapes.

⚠ `thinking_model: true` asks the provider for `{"effort": "medium"}` reasoning, unless
`llm.reasoning` (or `steps.score_sequences.reasoning`) already says how much to think. It does
nothing on a model without reasoning support, and the reasoning *text* comes back only from
the providers listed in [`providers.md`](providers.md).

## Phase 3: Task & Trajectory Generation

### 11. execute_sequences

**Purpose:** Pair each graph with initial states and **actually execute** the tools, so queries
are written against real inputs and outputs.

**Type:** deterministic (`requires_llm = False`), run through
`run_batch(graph_path, env_data_path, output_dir)`.

**Input:** `plan_sequences/multi_turn/all_sequences.jsonl` **and**
`sample_arguments/success.jsonl`.

**Process, per category:**
1. Execute the environment class once to read `function_name_mapping()`; build a spec lookup
   from `api_list`; collect the initial states from the `sample_arguments` rows; build the
   **sample bank** `{tool_name: [argument dicts]}` from `functions[].cases[].details|input`.
2. Shuffle the category's graphs with `random.Random(shuffle_seed)` **before** applying
   `max_samples_per_category`. Without this the input's turn-ordered blocks would exhaust the
   cap on 2-turn samples and starve the 3- and 4-turn ones. Seeded, so it is reproducible.
3. Pair each graph with `states_per_sequence` states (round-robin over the state list).
4. **Sequence records:** per turn, topologically sort the subgraph (Kahn; a cycle appends the
   remainder in input order), resolve each tool's arguments — explicit-edge outputs from
   already-executed tools first, then the sample bank (skipping `database_index`) — and run the
   tool with `safe_execute_tool` (20 s wall-clock bound). Bridge edges from earlier turns are
   included, so a later turn genuinely consumes an earlier turn's output.
5. **Multipath records:** re-enumerate the paths for each multipath pair (≤ 10 paths, depth
   `len(nodes)`), and run each path from a **fresh** environment instance.

**Output path:** `execute_sequences/pre_query_all_modes.jsonl` (**not** `success.jsonl`), plus a
`failed.jsonl` listing skipped `(graph, state)` pairs and a reason.

**Output fields:** `mode: "class_multi_turn"`, `type`, `id`, `initial_state`,
`database_index`, `category_name`, `number_turns`, `data_list`, `tool_code`, `api_list`;
multipath records add `nodes`, `edges`, `multipath_pairs`, `executed_paths`.

**Config:** `states_per_sequence: 2`, `max_samples_per_category: 50000`, `shuffle_seed: 42`
(the seed is a code default; it is not in `base.yaml`).

⚠ **`max_samples_per_category` caps every stage after this one.** It is the single most
effective cost control in Phase 3.

⚠ **Every row carries a full copy of `tool_code` and `api_list`.** The file grows fast,
and so does everything downstream that copies the row forward.

⚠ **One environment class per category** — the first `sample_arguments` row's — is used for all
of that category's states.

⚠ **A failing tool call does not fail the item.** It is recorded with `"success": false` and a
null output, and the row is still emitted; only a completely empty `data_list` (or empty
`executed_paths`) is a failure. Grep `pre_query_all_modes.jsonl` for `"success": false` before
concluding the generated environment works.

⚠ `safe_execute_tool`'s timeout bounds how long the *caller waits*. Python cannot kill the
thread: an abandoned call keeps running until the process exits.

---

### 12. generate_queries

**Purpose:** Write the natural-language user request that the executed chain answers.

**Input:** `execute_sequences/pre_query_all_modes.jsonl`.

**Routing** — two axes, six prompt paths:

| | `tools_only` | `with_user_and_policy` | `with_user` |
|---|---|---|---|
| `type: sequence` | fixed queries, one per turn | scenario + domain policy | scenario, no policy |
| `type: multipath` | one declarative query, several valid paths | multipath scenario + policy | multipath scenario |

The environment type comes from `env.get_environment_type(category)` — see
[`environment_types.md`](environment_types.md). The step stamps
`query_type = "<graph_type>_<environment_type>"` and `mode = "class_multi_turn"`.

**Then two more model calls per item:** a ground-truth plan (`<ground_truth_plan>`) and a
complexity classification (`<scenario_complexity>`).

**Output fields:**

| field | shape |
|---|---|
| `query` | **list** of `{"query": …}` (`tools_only` sequence, one per turn) · **dict** with `scenario` (either `with_user*` type) · **dict** with `query` (`tools_only` multipath) · the string `"Error"` |
| `query_type` | e.g. `sequence_tools_only`, `multipath_with_user_and_policy` |
| `ground_truth_plan` | dict, raw string, or `None` |
| `query_complexity` | dict or `None` — never a raw string, unlike `ground_truth_plan`: `_classify_complexity` assigns the unparsed string but does not `return`, so the unconditional `= None` after the loop overwrites it |

**Validator:** fails when `query` is missing, empty, or literally `"Error"`.

**Config:** `temperature: 0`, `max_tokens: 32000`, `max_attempts: 5`, and the opt-in
`few_shot` block (`enabled`, `num_examples`, `examples_path`, `examples`).

⚠ **At least three model calls per item**, and up to `max_attempts` attempts each for
the query and the plan. This is the second-most expensive LLM stage after `debug_environment`.

⚠ **The `with_user` and `with_user_and_policy` paths require the model to return a dict
containing `scenario`.** Anything else
is retried and then becomes `"Error"`, which the validator rejects. If a whole category fails
here, check that first.

⚠ **Tool specs shown to the query writer come from the input catalog** (`env.get_api_catalog`),
not from the generated environment class. If the two have drifted, the query can ask for
something the environment cannot do.

⚠ Few-shot examples are pooled from most general to most specific — `"*"` → environment type →
exact flow → `category_name` — deduplicated, then randomly sampled to `num_examples` with a seed
derived from the record id (reproducible per record, different across records).

### 13. generate_trajectories

**Purpose:** Drive a multi-turn conversation against the live environment.

**Input:** `generate_queries/success.jsonl` at `--iter 0`; `<category>/iter_<k>/input.jsonl`
afterwards.

**Output path:** `<category>/iter_<k>/trajectories/<label>/success.jsonl`, where `<label>` is
`--output-label` and defaults to `steps.generate_trajectories.tool_call_format`, so the folder
always describes what is in it.

**Tool-call format resolution:** `steps.generate_trajectories.tool_call_format`, else a
per-item `"tool_call_format"`, else `reasoning` when the step's `thinking_model` or the
item's `thinking_mode` is true, else `native`. The resolved value is stamped back onto the
record as `tool_call_format`, which `judge_trajectories` and `export_dataset` both read.

| `tool_call_format` | protocol |
|---|---|
| `native` | provider-native function calling; assistant `tool_calls`, results as `role: tool` |
| `reasoning` | tool specs rendered as text inside `<tool>`; calls parsed from `<tool_call>`; results returned as a user message; `reasoning_content` kept per message |
| `tagged` | assistant explains, then emits `<tool_call>{...}</tool_call>`; results come back as a **user** `<tool_response>...</tool_response>`; the run ends with `<answer>...</answer>` |

**Execution paths** — `{tools_only, with_user_and_policy, with_user} × {native, reasoning}`,
plus `tagged`:

- **tools_only** — no simulated user. One user message per turn query; the assistant calls
  tools until it answers.
- **with_user_and_policy** — a simulated user agent opens the conversation from the scenario,
  the assistant responds under `policy_rules`, `transfer_to_human_agents` is appended to the
  tool list, and the run ends on a terminate tool or `###STOP###` from the user.
- **with_user** — same simulated user, no policy text, **no transfer tool**; either side can
  emit `###STOP###`.

The `tagged` path additionally strips fabricated `<tool_response>` blocks (models not trained
for the protocol like to invent them), removes a premature `<answer>` when the model also
emitted tool calls, and wraps the final message in `<answer>` tags if the model forgot them.

**Output fields:** `conversation` (list of role/content dicts), `tool_call_format`, and
`thinking_mode: True` on the reasoning paths.

**Validator:** `conversation` must be a list of at least 3 messages; if exactly 3, the last
must have content.

**Config:** `temperature: 0.7`, `max_tokens: 2048`, `max_turns: 100`,
`max_tool_calls_per_turn: 30`, plus the user-simulator keys below.

⚠ **`max_turns` does not mean the same thing in every path.** In `tools_only` + `native` it
bounds tool-call *rounds within one user turn* (the number of user turns is
`len(turn_queries)`). In the `with_user*` native paths it bounds the whole assistant loop. In
the reasoning user-scenario path it is read with a default of 80. `max_tool_calls_per_turn`
(30) bounds the reasoning fixed-query and single-query loops, and the `tagged` loop.

⚠ **`thinking_model` selects the format, but not the folder name.** With `tool_call_format`
unset and `thinking_model` true, `_resolve_style` returns `reasoning` and the reasoning path
does run. The folder is named separately by `_resolve_output_label` in
[`vulcan/cli.py`](../vulcan/cli.py), which reads only `defaults.thinking_model` — so
`thinking_model` set under `steps.generate_trajectories:` produces reasoning data in a folder
called `native`. Set `tool_call_format: reasoning` explicitly and the two agree.

⚠ **The user-simulator keys are read flat from `steps.generate_trajectories`:** `simulated_user_model`,
`simulated_user_temperature`, `simulated_user_max_tokens`, `simulated_user_name` — each falling back to the step's own
`model` / `temperature` / `max_tokens`. The step reads no nested sub-dict, so a value tucked
under a `user_agent:` key would be ignored.

⚠ **`tool_call_format: tagged` only changes the `tools_only` path.** A category whose
`environment_type` is `with_user_and_policy` or `with_user` falls through to the native path
regardless, so a run configured for `tagged` can produce native function-calling trajectories
in a folder named `tagged`.

⚠ **Only the `tools_only` + `native` path normalises tool schemas.** `_build_native_tool_specs`
applies `normalize_schema` (drops `response`/`constraints`, maps `dict`→`object`,
`float`→`number`, `int`→`integer`, adds missing `items`). The `with_user*` native paths send
catalog specs verbatim, so a catalog using `"type": "dict"` or an `array` without `items` can
be rejected by a strict provider.

⚠ **`max_tokens: 2048` is per model call, not per trajectory** — fine for `native`, far too
small for `reasoning`. `quickstart` and `mock_test` raise it to 32000; `hotel_policy` does
not override it, so that config runs at 2048.

⚠ **Tool execution here has no timeout.** `generate_trajectories` uses `execute_tool`, unlike `execute_sequences`
which uses the bounded `safe_execute_tool`. A generated tool that loops forever stalls a worker
for the rest of the run.

⚠ **`generate_trajectories` and `judge_trajectories` run with `max_retries = 0`**, unlike every other
`PipelineRunner` stage. A failure here does not get another attempt in the same invocation.

### 14. judge_trajectories

**Purpose:** Judge trajectory quality and task completion. This is the gate on the SFT set.

**Input:** `<category>/iter_<k>/trajectories/<label>/success.jsonl`.
**Output path:** `<category>/iter_<k>/judged/<label>/success.jsonl`.

**Process:** route on `env.get_environment_type(category)` and on the tool-call format,
resolved as: the record's `tool_call_format` (stamped by `generate_trajectories`) →
`steps.judge_trajectories.tool_call_format` → `thinking_mode` → a heuristic on the trajectory's
system message (`<answer>` and `<tool_call>` present ⇒ `tagged`) → `native`.

For `native`, the tool specs are passed to the judge separately, because they are not in the
conversation. For `reasoning` and `tagged` they are already inside the trajectory's system
message, so the judge prompt does not repeat them.

**Output fields:** `judgment` — a dict holding `score` (1–10), `task_completed`, and
the written analysis. `export_dataset` reads both from inside this object.

**Validator:** `judgment` present and not `None`.

**Config:** `max_tokens: 16000`, and `model`.

The judge's model resolves like any other step's — `steps.judge_trajectories.model` → `defaults.model`
→ the model its client was built with — so a run that switches provider needs no change here.
Set `steps.judge_trajectories.model` (and optionally `steps.judge_trajectories.provider` / `base_url`) only to
judge on something other than what generated the data.

⚠ **`temperature` and `thinking_model` are hardcoded** (`0` and `False`) in the step. Setting
them under `steps.judge_trajectories` does nothing — [`vulcan/config/example_environment.yaml`](../vulcan/config/example_environment.yaml)
says so in a comment.

⚠ The judge receives the conversation interpolated as a Python list repr, not JSON. It is
readable, but do not expect valid JSON if you parse the prompt.

⚠ **The `thinking_mode` fallback resolves to the literal `thinking`**, which matches neither
the `reasoning` nor the `tagged` branch — so a record that carries no `tool_call_format` stamp
is judged with the `native` prompts, tool specs passed separately. Records written by
`generate_trajectories` always carry the stamp; hand-assembled ones may not.

⚠ `with_user` + `reasoning` reuses the **`tools_only`** reasoning judge prompts, so that
combination is judged without any domain framing.

## Phase 4: Selection & Output

### 15. export_dataset

**Purpose:** Filter judged trajectories and emit training records.

**Type:** deterministic (`requires_llm = False`). Unlike every other stage it runs **once
across all categories**, reading every `<category>/iter_<k>/judged/<label>/success.jsonl` — so
`native`, `reasoning`, and `tagged` output for the same iteration are merged.

**Process, per item:**
1. Parse `judgment` (accepts a dict or a JSON string; reads `score` and `task_completed`, each
   with a legacy alias fallback for records emitted before the field rename).
2. Select when `score >= min_score` **and**, if `require_task_completed`,
   `task_completed` is true.
3. Reconstruct:
   - `tool_call_format == "tagged"` → tagged format, **JSON only** (`_training_xml` is `None`).
   - `thinking_mode` → reasoning JSON + reasoning XML.
   - otherwise → function-calling JSON + XML.
4. Validate the reconstruction: chat template (optional `system`, then strict `user`/`assistant`
   alternation with no consecutive same-role messages), one `<tool_response>` per `<tool_call>`,
   and no empty assistant message. **A validation failure flips `_selected` back to `False`**,
   with the reasons in `_validation_reasons`, and the item is routed to the next iteration.

**Output structure** — one JSON file and one XML file per category per iteration:
```
training_dataset/
  json/<category>_iter_<k>.jsonl
  xml/<category>_iter_<k>.jsonl
```
Rejected items go to `<category>/iter_<k+1>/input.jsonl` with `conversation`, `thinking_mode`,
`judgment`, and this step's own annotations stripped, ready to be regenerated.

**Config:** `min_score: 8`, `require_task_completed: true`.

⚠ **The JSON and XML files are the same conversations in two wire formats**, not a
reasoning/non-reasoning split. Both are always written, except for `tagged` records, which are
JSON-only.

⚠ **The training record's system prompt is rebuilt from `api_list`; the trajectory's own system
message is dropped.** The policy is re-injected rather than carried over: the step resolves
`env.get_environment_type(category)` per record and, for `with_user_and_policy`, passes the
category's `policy_rules` into the reconstruction — via `reconstruct_policy_fc_json` / `_xml`
for `native`, and via `prepend_policy()` for `reasoning` and `tagged`, whose templates have no
`{domain_rules}` slot. `prepend_policy` is idempotent, never adds a second system message, and
is a no-op for `tools_only` and `with_user`. Covered by `tests/test_policy_in_export.py`.

**Rebuilt specs use the original `function`**, never `normalized_schema` — `_get_tool_specs`
reads `api.get("function", api)`. That is deliberate, not an oversight: records meant for
training on a tool set have to carry *your* tool definitions, not ones the pipeline reworded.
See [Your schemas, not VULCAN's](README.md#things-that-surprise-people).

⚠ **Nothing runs the next iteration automatically.** `iter_<k+1>/input.jsonl` is written and
then sits there; re-run `generate_trajectories` → `judge_trajectories` → `export_dataset` with `--iter 1`.

⚠ The record `id` is `_item_id` for `native`/`reasoning` records but the item's `id` for
`tagged` records, and the category key is `category_name` for the former and `category` for
the latter.

## Cross-cutting behaviour

**Resume is keyed on the input hash.** `PipelineRunner` assigns `_item_id = md5(json(item))`
over the item's *input*. Rows already in `success.jsonl` are skipped on re-run, rows in
`failed.jsonl` are retried, and a stale `processing.jsonl` from a crash is finalised first.
Changing the model or temperature does **not** invalidate anything — delete the stage's output
directory to force regeneration.

**Retries.** `defaults.max_retries` (10) applies to `PipelineRunner` stages; `generate_trajectories` and
`judge_trajectories` are constructed with 0. The three batch stages have no retry mechanism at all.

**Per-item failure never aborts the batch.** Workers catch `StepError` and every other
exception per item, write the row with `_validation_passed: false` and `_validation_reason`,
and continue.

**The optional `verification:` block is not the `judge_trajectories` judge.** When
`verification.enabled` is true, `StageVerifier` runs *after* a step's own validator for each
stage listed in `verify_steps`, and a rejection demotes the item to `failed.jsonl`. It reads
`model` / `max_tokens` / `temperature` from the `verification` block itself (an unset `model`
means the stage client's own), truncates string fields at 3000 characters, and caps the verdict at 512
tokens — so its rejections are unreliable on large items, which is why it ships disabled. An
`LLMError` from the verifier propagates rather than silently rejecting every item.

**Logs.** The whole tree is rooted at `<output_base>/logs/`, because `StageRunner` builds the
`PipelineLogger` with that directory: `<output_base>/logs/pipeline.log` (global),
`<output_base>/logs/<category>/pipeline.log`, and `<output_base>/logs/<category>/<step>.log`
per step, the last carrying `llm_calls=` and token counts.
